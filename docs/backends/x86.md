# x86 backend (`gpt-rs-backend-x86`)

The x86 backend compiles each function through the multi-level IR. Its pipeline runs, in order:

1. the passes over `tensor` but `merge-contracted-axes`;
2. `tensor-to-tile`, `pad-with-identity`, `inline-static-maps`, `canonicalize`, `widen-reused-maps`,
   `plan-layouts`, `canonicalize` again, `widen-narrow-floats`, which computes the ops on bf16 and
   f16 in f32, `expand-math`, which writes the math functions of f32 as polynomials, and
   `expand-random`, then `winograd-conv` and `canonicalize` when its options ask for it;
3. `form-groups` and `seal-dispatches`;
4. the schedule of each dispatch for its target: `name-target`, `select-atoms`, `split-lane-folds`,
   `schedule`, `place-epilogues` and `walk-order-layouts`;
5. `outline-static`;
6. the lowering to the buffer form: `tile-to-loop`, `canonicalize`, which composes and reduces the
   index math, `contract`, `loop-to-isa` and `plan-memory`.

It writes each function as C with AVX-512 intrinsics and OpenMP: a step function, `gptrs_step`, that
runs the function's launches in order, and its dispatches. It compiles the C with clang and runs a
function as one call of its step. An op left outside a dispatch, other than a constant or a host op
of the buffer form, is a compile error: the backend computes every op in its C.

Source of truth: [../../crates/gpt-rs-backend-x86/src/lib.rs](../../crates/gpt-rs-backend-x86/src/lib.rs).

- The target is the one the program states where it starts, resolved once into the backend:
  the CLI's `--target`, Python's `load_model(target=..)`, or `$GPTRS_TARGET`, and `host` by default
  (`gpt_rs_backends::BackendOptions`). It is a preset, `host` or a target file (`gpt-rs-cli target
  list`), and must have AVX-512. A target file may start from another target with
  `base = "<preset or file>"` and state only what differs; the module doc of
  [`gpt_rs_ir::targets`](../../crates/gpt-rs-ir/src/targets/mod.rs) gives the format. Every pass
  that needs a target takes the backend's, and the program cache keys programs by it.
- Off by default: `--winograd` (Python `winograd=True`, `$GPTRS_WINOGRAD=1`) adds `winograd-conv`
  after `expand-random`, then `canonicalize` again: each 3x3 convolution with stride 1 runs as
  Winograd's F(2x2, 3x3), which rounds differently from the convolution.
- Each weight is read in place, from the memory of its checkpoint, through C types aligned to 1
  byte. No pass lays one out at load time. Where a cache keeps a piece of a weight that the tiles of
  rows share, and the piece's lines would crowd the cache's sets, a worker reads it from a copy that
  it makes in its scratch (`held copy`). It does so when `schedule` counts that as moving fewer
  bytes than reading the weight again for each tile of rows.
- In the step function, each op of the buffer form is C ([../ptir/host.md](../ptir/host.md)):
  an arena or a slice of one is an address, a launch a call of its dispatch, a copy a `memmove`,
  and a result that an arena holds a `memmove` into memory of its own. The runtime gives it the
  memory of the function's arguments, allocations and constants, and checks each argument against
  the function's argument types before the call. While a profile collects, the step calls back
  before and after each launch, which the profile reports as `x86_backend.dispatch`.
- Every `loop.func` becomes one C function, `gptrs_run_<name>`, which the step calls; it is never
  inlined into the step, whose registers it would share. A `loop.forall` is an OpenMP parallel
  loop with a static schedule on the units of its execution level: one thread per iteration, at
  most one per unit, whatever `OMP_NUM_THREADS` says. Where the target lists the CPUs of each
  unit, as `host` does, each worker thread pins itself to the CPUs of its unit, once, and the
  thread that runs the step runs the first iteration where it is. Otherwise where the threads run
  is OpenMP's: `OMP_PLACES=cores OMP_PROC_BIND=close` puts one thread on each core, in order, and
  `gpt-rs-cli` sets them when the environment places no threads itself. `$CC` must link OpenMP
  (`-fopenmp`). A `loop.forall` inside another one is an error.
- The C computes what the interpreter computes of the `isa` program, bit for bit, with
  `-ffp-contract=off` and no fast math. The rounding changes against the `tile` program are those
  that the dispatch's `numerics` name, and `expand-math`'s polynomials for `exp`, `tanh`, `log`,
  `sin`, `cos` and `erf`: on every f32 input within 1 ulp of the interpreter's function, the
  `libm` crate's f64 function rounded to f32.
  On a target with FMA a dispatch contracts (`numerics = <contract = true>`): `tile-to-loop` marks
  its `loop.func`, and `contract` turns each f32 or f64 product in it and the sum it enters into
  one `arith.fma`, which the C writes as `_mm512_fmadd_ps` or `_mm512_fmadd_pd`, or as
  `__builtin_fmaf` or `__builtin_fma` on scalars.
- Each op that computes in a dispatch is C operators, builtins, intrinsics, or one of the preamble's
  inline conversions. Where its threads pin themselves, a `loop.forall` also calls
  `omp_get_thread_num` and `gptrs_pin`. The x86 rules (`gpt_rs_ir::dialects::x86`) give the form of
  each `isa` op, the extensions it needs, the mask and vector registers it holds and the operands it
  reads from memory. `loop-to-isa` checks these against the target. Float `maximum` and `minimum`,
  which give a NaN for any NaN operand, are AVX-512DQ's `vrangeps`, which orders the zeros as they
  do and drops a quiet NaN, with the sum of the operands, a NaN, where either is NaN. Against a
  constant, they are one comparison and a blend.
- clang vectorizes nothing itself (`-fno-vectorize -fno-slp-vectorize`): the C is vectorized as the
  schedules of its dispatches say. It turns no loop into a library call either (`-fno-builtin`): a
  loop that zeroes a private array stays stores, so no register is saved across a `memset` in it.
- A `reg` buffer is held in vector variables, so a register tile's accumulators stay in registers
  through its reduction loop: `loop-to-isa` checks that only whole registers at positions fixed
  before the run reach it.
- The code of a register tile is written register by register, in the order of the register model
  (`isa::RegisterCode`): for each row, its broadcast, then each vector's fma, or product and sum. So
  the C holds at once what the model counts: the accumulators, a row of what repeats along the rows,
  the broadcast in use, and a product unless an fma adds it. clang keeps the order of the C
  (`-mllvm -enable-misched=false`). Its scheduler would otherwise start every load of a tile first
  and hold them all in registers. clang keeps a constant as a memory operand of each op that reads
  it (`-mllvm -disable-machine-licm`), as the model counts it, rather than a register held through
  the loop. Its instruction selection still starts loads early, such as the next row's while the row
  before is in use, so an empty `__asm__ volatile("")` comes before each loaded register: clang
  moves no memory access across it.
- clang moves nothing between the parts the schedule runs one after another. It unrolls no loop
  (`#pragma clang loop unroll(disable)`). It moves no memory access across the end of a sequential
  loop (an empty `asm` that clobbers memory). It keeps a private array with axes in memory (its
  address goes to an empty `asm`). Otherwise it holds the sums of one register tile, or of a
  private array, in registers while another tile's loop runs. A private cell, which has no axes,
  is a variable that clang may keep in a register.
- A padded read checks only the coordinates, and the run of lanes, that its `checked` attribute
  names for each register: those that the loops around it do not keep inside its buffer, which
  `loop-to-isa` finds from the bounds of those loops and the interpreter checks. A load whose lanes
  are all inside wherever its condition holds loads them, or is the pad, without a mask.
- No vector or mask spills. `loop-to-isa` fails when a register tile's code holds more vector or
  mask registers at once than the target has, as the register model counts them. Compiling fails
  when the assembly (`program_<hash>.s`) spills a vector or mask register anywhere, by clang's
  comments on its spills; the error names each spill, the op its line comes from and the line of
  Rust that recorded it. So `$CC` must be clang.
- Memory follows the plan of `plan-memory` ([../ptir/host.md](../ptir/host.md)):
  - The function keeps its arenas from one call to the next, so the values between its launches
    live in memory that is already mapped. Each `host.arena` op has memory of its own.
  - Each result that the function allocates takes new memory.
  - An arena starts at a multiple of the alignment of its `host.arena`, and the runtime fails a
    run whose new memory for a `host.alloc` does not start at a multiple of its alignment: the
    alignment of buffers that the target states, 64 bytes on the x86 presets.
  - A launch updates in place the tensor of `host.take`, such as a KV cache, when the caller holds
    it no more. The graph runtime gives a run the handle of an input that no tensor holds and no
    pending value reads, and the backend copies the tensor only when another handle holds it.
- Libraries are cached in the process and on disk, in `$GPTRS_X86_CACHE_DIR` or `gpt-rs/x86` in the
  user's cache directory (`$XDG_CACHE_HOME`, else `~/.cache`), created readable by the user alone,
  and keyed by the C source, the compiler and its flags. They have debug info, and each line that an
  op writes ends with its op's number among the program's ops. `program_<hash>.map.json`, beside the
  C, gives each line's op number in the dump, its location and its trail ([../perf.md](../perf.md)).
- Its lowering is part of its pipeline, so `--dump-dir` dumps the module after each of its passes,
  and the C and its line map when a function compiles.
- It reads, writes and converts bf16 and f16 elements, 16 lanes in a 256-bit register beside 16
  f32 lanes, and computes on them in f32, as the IR converts them: exactly to f32, and back rounded
  to nearest-even. It reads FP8 (e4m3, e5m2) elements and converts them to f32 exactly. It computes
  `rng_uniform` through the integer ops of `expand-random`, and writes no C for `rng_normal`:
  compiling a function that has it fails with the op it lacks.

## Backend name

The backend's name is `x86`, the name that `gpt_rs_backends::load_model` and the CLI's
`--backend` take.
